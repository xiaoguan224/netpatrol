# netpatrol · 网络设备日志智能巡检工具

一个零第三方依赖的 Python 小工具：读取华为 / eNSP 风格的路由器、交换机日志，自动完成
**解析 → 事件分类 → 统计异常检测 → 生成巡检报告（Markdown / HTML / JSON）**。

设计目标不是做一个"完美复刻商业网管"的产品，而是把课堂上分散学到的东西
（设备日志格式、eNSP 拓扑、Linux Shell、Python 数据处理、统计基线）串成一条**能跑通、能演示、能解释**的
自动化运维管道 —— 也就是"智能网络运维 / AI 技术支持"岗位里最真实的那个日常：
**值班人员第二天早上打开的，不是一堆 `.log`，而是一份带优先级和证据的巡检报告。**

```
接口抖动      →  5 分钟窗口内 UP/DOWN 翻转次数      →  P1
暴力破解      →  同一源 IP 认证失败聚类（10 分钟 ≥5 次）→  P0
协议邻居异常  →  OSPF/BGP/VRRP 邻居 Down/主备切换关键字  →  P1
异常时段操作  →  凌晨 0-6 点的配置/命令记录            →  P1
日志频率突增  →  模板归一化 + 滑动窗口 + 均值 3σ 基线   →  P2
未知事件      →  首次出现的日志模板（novelty）         →  P3
```

## 快速开始

只需要 Python 3.10+，**不用 pip install 任何东西**。

```bash
# 1) 内置样例日志跑完整流程（含 5 类埋点异常）
python -m netpatrol demo

# 2) 分析自己的日志（支持多文件、HTML 报告、阈值调节）
python -m netpatrol analyze router.log swCore.log -o reports --html
python -m netpatrol analyze router.log --window 3 --min-fail 8 -v

# 3) 单元测试
python -m unittest discover tests -v
```

`demo` 输出示例（样例日志 161 行，全部解析成功）：

## 实现要点

**解析层** —— 华为日志的时间戳有三种常见写法，实测都出现过：
`Jul 10 2026 14:02:00.100`（年中）、`Jul 10 08:23:45 2026`（年尾）、`Jul 10 2026 08:23:45:100`（冒号毫秒）。
`HUAWEI_RE` 用「年-时 | 时-年」两条分支显式匹配，`parse_ts` 再把毫秒分隔符（点/冒号）和时区后缀统一剥掉，
缺年份的行按文件上下文年份补齐。日志行里的 IP / MAC / 接口名 / 数字会被替换成 `<IP> <MAC> <IFACE> <N>`，
得到**日志模板（template）**——这是后面做频率基线和"首次出现事件"检测的基础，思路来自 LogSig / Drain 这类日志解析研究。

**分类层** —— 规则库按模块名 + 关键字把事件分成 接口链路 / 认证安全 / 路由协议 / 系统资源 / 配置变更 / VPN隧道 六类，
先看模块名命中，再看消息正则兜底（可解释、误报可控，比黑盒分类器更适合运维场景）。

**检测层** —— 全部是**统计规则**而非机器学习模型：抖动看窗口内状态翻转次数，爆破看同源 IP 失败聚类，
频率突增用 5 分钟桶的 均值 + 3σ 基线，novelty 看模板是否首次出现。选择统计规则的理由很直接：
运维日志的"正常"没有标签可学，而 3σ / 滑动窗口这类方法**可解释、可阈值调节、能在没有训练数据的新设备上直接上线**。

**报告层** —— 结论由"发现类型 → 处置建议"映射表生成（例如暴力破解 → 核查源 IP 并考虑 ACL 封堵 + 改 SSH 端口/密钥登录）。
可选接一个大模型对结论做文字润色，只通过环境变量启用，不配也能跑：

```bash
export NETPATROL_LLM_API="https://<你的兼容OpenAI接口>/v1"
export NETPATROL_LLM_KEY="sk-..."     # 只在运行时读取，仓库里没有任何密钥
export NETPATROL_LLM_MODEL="gpt-4o-mini"
```
润色失败会自动回退到规则生成的结论，保证巡检不中断。

## 关于样例数据

`samples/huawei_router_demo.log` 由 `tools/make_sample.py` 生成（`random.seed(42)`，可复现）：
5 类人为埋入的异常 + 120 行正常噪声，格式对齐 eNSP / 华为 USG、AR 系列路由器的 `%模块/级别/代码` 结构。
**它是模拟数据，不是真实生产日志** —— 换成你自己 eNSP 里 `display logbuffer` 导出的文本就能直接分析。

## 面试考点自查

- 为什么不用机器学习模型？→ 无标签、需要可解释、阈值要能现场调；统计基线是工业界日志告警的主流第一层。
- 日志模板归一化解决什么问题？→ 把 `Gig0/0/1 断开` 和 `Gig0/0/2 断开` 视为同一类事件，才能统计频率、才能识别"新类型"。
- 3σ 基线的坑？→ 突发但不异常的操作（割接窗口）会误报，实践上要做维护期抑制 / 分时段基线。
- 为什么把"凌晨配置操作"单独列出来？→ 这是安全与运维的交叉点：合规上异常时段变更需审批，也是横向移动的典型特征。
- 怎么扩展到真实环境？→ syslog 实时接入（`socketserver`）、多设备拓扑关联（同一故障在下游会引发风暴，需要根因收敛）、告警去重与静默。

## 已知局限（诚实地写在这里）

多厂商格式只覆盖华为 + 通用 syslog，思科/Cisco IOS-XR 原生时间戳未适配；没有实时 syslog 监听（只做离线批处理）；
跨设备的根因收敛（一场链路故障引发 20 台设备告警风暴）尚未实现，属于下一阶段工作。
