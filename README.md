# netpatrol · 网络设备日志智能巡检工具

仓库：<https://github.com/xiaoguan224/netpatrol>

一个零第三方依赖的 Python 小工具：读取华为 / eNSP 风格的路由器、交换机日志，自动完成
**解析 → 事件分类 → 统计异常检测 → 生成巡检报告（Markdown / HTML / JSON）**。

设计目标不是做一个"完美复刻商业网管"的产品，而是把课堂上分散学到的东西
（设备日志格式、eNSP 拓扑、Linux Shell、Python 数据处理、统计基线）串成一条**能跑通、能演示、能解释**的
自动化运维管道 —— 也就是"智能网络运维 / AI 技术支持"岗位里最真实的那个日常：
**值班人员第二天早上打开的，不是一堆 `.log`，而是一份带优先级和证据的巡检报告。**

```
接口抖动      →  5 分钟窗口内 UP/DOWN 翻转次数      →  P1
暴力破解      →  同一源 IP 认证失败聚类（10 分钟 ≥5 次）→  P0
协议邻居异常  →  OSPF/BGP/VRRP 邻居 Down/主备切换关键字  →  P1
异常时段操作  →  凌晨 0-6 点的配置/命令记录            →  P1
日志频率突增  →  模板归一化 + 5 分钟固定分桶 + 均值 3σ 基线   →  P2
罕见错误模板  →  错误级及以上、全量只出现一次的日志模板   →  P2
```

## 快速开始

只需要 Python 3.10+，**不用 pip install 任何东西**。

```bash
# 1) 内置样例日志跑完整流程（含 6 类埋点异常）
python -m netpatrol demo

# 2) 分析自己的日志（支持多文件、HTML 报告、阈值调节）
python -m netpatrol analyze router.log swCore.log -o reports --html
python -m netpatrol analyze logs/R1-logbuffer.log --window 3 --min-fail 8 -v

# 3) 现场收日志：设备 info-center loghost 指向本机，UDP 落盘
python tools/syslog_sink.py --out logs/R1-live.log --port 5140

# 4) 单元测试
python -m unittest discover tests -v
```

## 实现要点

**解析层** —— 字段顺序按华为官方《信息的输出格式》实现：`时间戳 [时区] 主机名 [IPv4] %%版本 模块/级别/名称(类别)[序号]: 描述`。
时间戳一共五种，`display logbuffer` 里能同时遇到：英文 `Jul 10 2026 08:23:45`、年尾写法 `Jul 10 08:23:45 2026`、
中文环境 `2026/07/10 08:24:02.123`、format-date `2026-07-10 08:24:31`、short-date `Jul 10 08:25:00`（无年份，按文件上下文补齐）。
毫秒分隔符可能是点也可能是冒号（`08:23:45:100`），时区后缀 `+08:00` 直接贴在秒后面，这些都在 `parse_ts` 里统一剥掉。
行前缀也分三种：缓冲区回显的 `%`、Trap 行的 `#`、发往日志主机时才有的 `<PRI>`；`(l)`/`(d)`/`(s)` 类别和 `[12]` 序号会被吃掉，
不会污染消息体和模板。至于终端复制下来的 `<R1>display logbuffer`、`---- More ----`、VRP 版本横幅、`% Invalid command`，
它们本来就不是日志，单独计入"跳过"而不是算解析失败。日志行里的 IP / MAC / 接口名 / 数字会被替换成 `<IP> <MAC> <IFACE> <N>`，
得到**日志模板（template）**——这是后面做频率基线和"首次出现事件"检测的基础，思路来自 LogSig / Drain 这类日志解析研究。

**分类层** —— 规则库按模块名 + 关键字把事件分成 接口链路 / 认证安全 / 路由协议 / 系统资源 / 配置变更 / VPN隧道 六类，
先看模块名命中，再看消息正则兜底（可解释、误报可控，比黑盒分类器更适合运维场景）。

**检测层** —— 全部是**统计规则**而非机器学习模型：抖动看窗口内状态翻转次数，爆破看同源 IP 失败聚类，
频率突增用 5 分钟桶的 均值 + 3σ 基线（基线用 leave-one-out 剔除待判定桶自身、空桶按 0 计入，
否则突发会把自己抬高到报不出来，详见下面真机记录二），novelty 看模板是否首次出现。选择统计规则的理由很直接：
运维日志的"正常"没有标签可学，而 3σ / 滑动窗口这类方法**可解释、可阈值调节、能在没有训练数据的新设备上直接上线**。

**报告层** —— 结论由"发现类型 → 处置建议"映射表生成（例如暴力破解 → 核查源 IP 并考虑 ACL 封堵 + 改 SSH 端口/密钥登录）。
可选接一个大模型对结论做文字润色，只通过环境变量启用，不配也能跑：

```bash
export NETPATROL_LLM_API="https://<你的兼容OpenAI接口>/v1"
export NETPATROL_LLM_KEY="sk-..."     # 只在运行时读取，仓库里没有任何密钥
export NETPATROL_LLM_MODEL="gpt-4o-mini"
```
润色失败会自动回退到规则生成的结论，保证巡检不中断。

## 关于样例数据与真实日志

`samples/huawei_router_demo.log` 由 `tools/make_sample.py` 生成（`random.seed(42)`，可复现）：
6 类人为埋入的异常 + 120 行正常噪声，格式对齐 eNSP / 华为 USG、AR 系列路由器的 `%%版本模块/级别/名称(l)[序号]` 结构。
**它是模拟数据，不是真实设备日志**，仓库里没有把它冒充成真机导出。

`tests/fixtures/vrp_formats.log` 里的行是按华为官方《信息的输出格式》文档和 eNSP 终端回显手工整理的**格式样例**，
用来钉住解析器契约（五种时间戳、`#`/`%`/`<PRI>` 前缀、`(l)[12]`、终端噪声行），同样不是真机日志。

### 换成真实设备日志的两条路

**A. eNSP 里直接取（最简单）** —— 2026-11-03 已用真机输出验过一轮，结果记在下面。

```
<AR1> system-view
[AR1] info-center enable                 # 实验时常常被 undo 掉了，先打开
[AR1] quit
<AR1> screen-length 0 temporary          # 关掉分页，一次打全，避免 ---- More ----
<AR1> display logbuffer                  # 交换机/USG 同命令；只看安全日志加 security
```
把窗口里的内容复制进 `logs/AR1-logbuffer.log`（记事本另存时选 UTF-8），然后
`python -m netpatrol analyze logs/AR1-logbuffer.log --html -o reports_real -v`。
提示符、`#`、`---- More ----`、VRP 版本横幅这些会被计入"跳过"，不拉低解析率。
要制造可检出的事件：`shutdown` / `undo shutdown` 一个接口做抖动，用错密码连几次 SSH 做认证失败，
凌晨时段改配置做异常时段操作。

**真机验证记录一（2026-11-03 17:39，eNSP V1.3.00.100 + AR，`display logbuffer` 原文，6 条）**

```
[ok] 解析 6 条事件（未识别 0 行，跳过非日志行 13 行，解析率 100.0%）
```

这份真机输出纠正了三个只看文档推不出来的事实：

1. **终端会在第 80 列硬折一行**，续行不带时间戳、还可能断在单词中间
   （`...GigabitEthernet0/0/1: chan` / `ge status to up`）。6 条日志就有 6 个折行，
   不拼回来的话事件描述被截断、模板归一化和频率统计全废 —— 解析器现在按"上一行满 80 列"判定并拼回。
2. **`display logbuffer` 开头有 7 行缓冲区统计**（`Logging buffer configuration and contents : enabled`、
   `Current messages : 6` 等），不是日志；连同命令回显一起计入"跳过"，6/6 条日志仍是 100% 解析率。
3. **时间戳带 `-08:00` 时区后缀**（eNSP 的 AR 默认时区不是东八区），而且真实模块名出现了
   `PHY` / `CFM` / `GTL` 三个规则库里没有的，已分别补进 接口链路 / 配置变更 / 系统资源。

**真机验证记录二（2026-11-03 18:06，两台路由器 R3/R4 的全量日志缓冲，共 237 行原文）**

```
[ok] 解析 76 条事件（未识别 0 行，跳过非日志行 161 行，解析率 100.0%），发现异常 19 项 P0=0 P1=15
```

161 行"跳过"里 **147 行是 80 列硬折的续行**（已经拼回对应事件，不是丢掉的日志），
另外 14 行是缓冲区统计头和命令回显；也就是说 100% 这个数不是靠把读不懂的行踢出去换来的。
分类结果：路由协议 40、接口链路 28、系统资源 6、配置变更 2；
模块出现了 `OSPF` / `IFNET` / `PHY` / `VOSCPU` / `GTL` / `CFM`，`VOSCPU`（CPU 过载告警）是第二轮补进规则库的。

真机上被检出的 4 类异常（19 项，每条都带原始日志行做证据）：

| 检测器 | 条数 | 真机现场 |
| --- | --- | --- |
| 接口抖动 | 3 | R3 的 Gi0/0/1、Gi0/0/2 与 R4 的 Gi0/0/1 在 5 分钟内 UP/DOWN 反复翻转 |
| 协议邻居/会话异常 | 12 | OSPF 邻居从 Full 掉回 Down，`NBR_DOWN_REASON` 给的原因是 `Hello Not Seen` 和 `1-Way hello Received` |
| 罕见高危错误模板 | 3 | 同一台设备上此前没出现过的 `NBR_DOWN_REASON` / `NBR_CHG_DOWN` 组合 |
| 日志频率突增 | 1 | 17:57 起 5 分钟 44 条（OSPF 邻居事件 21 + 链路状态 12），正是那次 OSPF 重收敛 |

**真机逼出来的第二个改动**：`detect_burst` 原来把待判定的那个桶也算进基线，
这批日志分桶是 16 / 16 / 44，含 44 算下来均值 25.3、σ 13.2、阈值 64.9 —— 最猛的 44 那条桶自己把阈值抬到报不出来。
现在基线改成 **leave-one-out（剔除待判定桶）+ 空桶按 0 计入**，同一份数据阈值 32.0、44 > 32 正常报出。
这条有单测钉住（`TestBurstBaseline`），别再退回旧写法。

**没在真机上复现的部分**（写清楚，免得面试问起来只能靠话术）：这份日志来自一次链路抖动 +
OSPF 重新收敛的实训操作，没有登录失败、没有凌晨变更、也没有 VPN 隧道事件，所以
**SSH 暴力破解、VPN 隧道、异常时段操作 3 个检测器在这批真机数据上是零输出**，只有样例日志的埋点场景验证过它们。
另外这批只有 76 条事件、跨 24 分钟，频率突增的基线只有 5 个桶，够用但谈不上稳。

## 面试考点自查

- 为什么不用机器学习模型？→ 无标签、需要可解释、阈值要能现场调；统计基线是工业界日志告警的主流第一层。
- 日志模板归一化解决什么问题？→ 把 `Gig0/0/1 断开` 和 `Gig0/0/2 断开` 视为同一类事件，才能统计频率、才能识别"新类型"。
- 3σ 基线的坑？→ 两个方向都会错：突发但不异常的操作（割接窗口）会误报，实践上要做维护期抑制 / 分时段基线；
  更隐蔽的是突发把自己算进均值和 σ、把阈值抬到自己头上导致漏报，所以我改成 leave-one-out 基线 + 空桶计 0，并有单测钉住。
- 那空桶计 0 会不会带来新问题？→ 会，而且我认了。日志一跨几天，绝大多数 5 分钟桶是空的，均值被压到 0.2、σ 也小，
  3σ 阈值就退化成摆设，真正起作用的是 `min_count=8` 这个绝对值下限（样例日志上就是这样）。
  代价是"平稳期每小时 50 条"这种基线本身很高的场景，涨到 9 条也会报。
  下一步要么按活跃时段算基线（只统计有日志的时段、但用 leave-one-out 避免自掩），要么换成稳健统计（中位数 + MAD）。
- 为什么把"凌晨配置操作"单独列出来？→ 这是安全与运维的交叉点：合规上异常时段变更需审批，也是横向移动的典型特征。
- 怎么扩展到真实环境？→ syslog 实时接入（`socketserver`）、多设备拓扑关联（同一故障在下游会引发风暴，需要根因收敛）、告警去重与静默。

## 已知局限（诚实地写在这里）

多厂商格式只覆盖华为 VRP + 通用 syslog，思科/Cisco IOS-XR 原生时间戳未适配；`tools/syslog_sink.py` 只负责收流落盘，
告警仍是批处理（跑一次 analyze 出一份报告），没有常驻判定与通知推送；
跨设备的根因收敛（一场链路故障引发 20 台设备告警风暴）尚未实现，属于下一阶段工作。
`info-center timestamp boot` 那种相对开机毫秒的时间戳不解析，因为无法定位绝对时间。
